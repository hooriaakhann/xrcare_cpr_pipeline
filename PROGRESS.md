**Pretrained checkpoint (`src/hybrid/models.py`, new):** `HAND_LANDMARKER` pins the official MediaPipe `hand_landmarker.task` (float16, Google's model repo) by exact URL + sha256. `ensure_model()` downloads into `paths.models_dir` (new config path, default `models/`, gitignored — large binary) only if missing, and verifies the checksum on every call, raising `ModelDownloadError` on failure/mismatch rather than silently using a possibly-wrong file. Pretrained only, never fine-tuned (CLAUDE.md rule 4) — the checksum is what makes "which checkpoint produced this run" reproducible without committing the binary.

**`src/hybrid/mediapipe_roi.py`:** `MediaPipeHandLocalizer` (VIDEO-mode `HandLandmarker`, one hand by default) detects per-frame: 21 hand landmarks (pixel coords), a tight bounding box, a **dynamic CPR-foreground ROI**, and a handedness-derived confidence score. The ROI is the tight bbox padded by `roi_padding_ratio`, then extended toward the forearm — continuing the middle-finger-MCP-to-wrist direction past the wrist by `forearm_extension_ratio x` the bbox's long side — so the region covers wrist + part of forearm, not just the hand, per spec. Never crops the frame itself; `HandDetection.image` is never stored, only coordinates, so the full frame stays available for Phase 4 ego-motion. `run_mediapipe_on_video()` iterates a whole video via the Phase 1 `VideoReader`, computes detection rate and longest no-detection gap (frames + seconds), logs a warning (not silent) when the gap exceeds `mediapipe.max_detection_gap_sec`, and raises `HandNotDetectedError` if the hand is never found in the entire video. `get_cotracker_init_points(detection, num_points)` returns the 21 landmarks first, then fills any remainder with a grid sampled over the ROI — this is what Phase 3 will call to seed CoTracker.

**Caching:** `run_mediapipe_on_video_cached()` wraps the above through the Phase 0.5 `CacheManager`, keyed by `(video_id, hash(mediapipe sub-config + pinned model sha256))` — scoped to only the MediaPipe config, so tuning unrelated parameters (Butterworth, fusion weights, ...) in later phases never invalidates this branch's cache.

**Dependency:** installed CPU-only PyTorch (`torch==2.13.0+cpu`, via the `download.pytorch.org/whl/cpu` index — avoids pulling multi-GB CUDA wheels on this GPU-less machine) into the *same* venv as MediaPipe. `pip check` clean, no conflicts — so ADR 0003's "isolated venv + subprocess" default (Phase 0.5) was **not needed** for CoTracker; deferred to Phase 10/RepNet, where a TF1/TF2-era research repo is more likely to actually collide with the main env. CI installs the CPU torch wheel explicitly too (same reasoning). `pyproject.toml` now lists `torch`.

**Memory-driven design constraint (found before writing any orchestration code):** the offline model holds its whole input video tensor in memory at once. At this dataset's native resolution (~2000x1500), a ~600-frame video would need **~20GB** just for the float32 tensor — this machine has 16GB total RAM (~8.9GB free). Confirmed via a timed smoke test on real frames (90 frames/40 points: 66s at native res, 55s resized to 2x model resolution — resizing barely helps *speed*, since CoTracker downsamples internally regardless, but it's a **hard memory necessity**, not just a speed optimization). This is why `src/hybrid/cotracker_tracker.py` processes videos in memory-bounded temporal windows (`cotracker.window_frames`, default 100) instead of Phase 3's naive one-call-per-video reading of the spec.

**`src/hybrid/cotracker_tracker.py`:** `run_cotracker_on_video()` iterates the Phase 1 `VideoReader` in windows. Each window's query points are either (a) the previous window's last tracked positions (continuing the same point identities — the normal case), or (b) freshly reseeded from MediaPipe's ROI/landmarks at the new window's start (a **reinit event**, logged) when the previous window ended with a visible-point ratio below `cotracker.reinit_visibility_threshold`. This directly implements the spec's "MediaPipe may periodically reinitialize CoTracker if tracking quality becomes poor" — the trigger is quality-based, not a hardcoded cadence, and doubles as the window-stitching mechanism (no overlap frames needed). Per-point-per-frame `tracks_x`/`tracks_y`/`visibility` are kept in full (spec: "x trajectory, y trajectory, visibility... for every tracked point over time"), plus `num_visible_per_frame`, `valid_ratio_per_frame`, `reinit_events`, and `track_loss_periods` (longest-contiguous-run detection, same pattern as Phase 2's `_longest_gap`, generalized to a threshold condition). `tracker_motion_y(t)` = **median Y of currently-visible points per frame** (per spec's suggested strategy, robust to outlier tracks vs. a mean) — this is the raw signal Phase 6-9 will filter/analyze for periodicity. Raises `TrackLostError` (logged) only if the longest track-loss period exceeds `max_track_loss_sec` **and** `max_reinits` is already exhausted — a transient dip that a reinit fixes is not a failure.

**Caching:** `run_cotracker_on_video_cached()`, same pattern as Phase 2, keyed on `(video_id, hash(cotracker sub-config + mediapipe sub-config + pinned HandLandmarker sha256))` — deliberately includes the MediaPipe sub-config too, since CoTracker's seed points depend on MediaPipe's output; a MediaPipe config change must invalidate CoTracker's cache even if no CoTracker parameter changed (verified by test).

**Config:** new `cotracker:` section matching the Phase 0.5 skeleton's example almost exactly (`num_points: 40`, `visibility_threshold: 0.6`, `reinit_visibility_threshold: 0.4`) plus the memory/windowing parameters this phase's real-data investigation showed were necessary: `max_reinits: 10`, `max_track_loss_sec: 2.0`, `window_frames: 100`, `working_max_dim: 1024`. All schema-validated (thresholds in [0,1], counts >=1, `max_reinits` >=0 — 0 is legitimate, meaning "never reinitialize," useful for later ablations).

**Tests (`tests/test_cotracker_tracker.py`, 15 tests; `tests/test_config.py` +13 for the new schema fields):** 14 fast tests — resize-for-memory geometry, longest-track-loss-run detection (mirrors Phase 2's gap tests), median-visible-Y aggregation (incl. all-invisible -> NaN), config-hash sensitivity, and 4 orchestration tests that **monkeypatch `_run_window`** (not the real model) to deterministically drive the windowing/reinit/track-loss state machine across multiple windows — verifying reinit-then-recovery, `TrackLostError` when sustained loss exhausts `max_reinits`, `TrackLostError` when a reinit is needed but no MediaPipe detection exists in that window, and immediate failure when MediaPipe never detected anything at all — plus 2 caching-wrapper tests. 1 `@pytest.mark.slow` test loads the real CoTracker checkpoint and runs it on a tiny synthetic clip with a locally-distinctive moving pattern, asserting well-formed output shapes/dtype and that query-frame points are returned unchanged. ## Phase 4 — RANSAC Affine Ego-Motion Compensation (done)

**Refactor before new code:** extracted `src/hybrid/signal_utils.py::longest_bad_run()` — the "longest contiguous run of a bad condition, plus every such run's span" logic had shown up identically in Phase 2 (`_longest_gap`) and Phase 3 (`_longest_run_below_threshold`); with Phase 4 needing the exact same pattern for unreliable-transform spans, that's the third occurrence, past the point where duplicating is the right call. Phase 3's `_longest_run_below_threshold` now delegates to it (same signature, same tests, all still passing — verified before writing any Phase 4 code). Left Phase 2's `_longest_gap` alone since it operates on a `list[HandDetection]` rather than raw arrays and touching already-shipped, tested code for a 3rd-instance-only benefit wasn't worth the risk.

**`src/hybrid/ego_motion.py`:** for every consecutive frame pair, detects background features via `cv2.goodFeaturesToTrack` with a mask that **excludes the current CPR ROI** (Phase 2's MediaPipe output, forward-filled across brief detection gaps, dilated by `roi_exclusion_dilate_px`) so compression motion can never leak into the camera-motion estimate; tracks them into the next frame with `cv2.calcOpticalFlowPyrLK`; fits a RANSAC-robust **similarity** transform via `cv2.estimateAffinePartial2D` (translation + rotation + uniform scale — 4 DOF, not the full 6-DOF `estimateAffine2D`). This is the Phase 4 "justify which estimator" requirement: a wearer's head motion is physically a similarity transform (no independent x/y scale or shear), so the extra 2 DOF of full affine would only fit noise — becomes ADR 0001 in Phase 20. Each pair gets a **fresh** feature detection rather than one long-lived track set — simpler, and self-correcting (one bad pair can't propagate into the next). `cv2.setRNGSeed(config.project.seed)` is set once per video for reproducible RANSAC, and the seed is recorded on `EgoMotionVideoResult` (feeds `summary.json`/ledger in Phase 16).

A transform is `transform_valid` only if inlier ratio, rotation magnitude, and scale all pass configured sanity bounds; `confidence` = inlier_ratio when valid, else exactly 0.0 ("driven toward zero" per spec) — never applied blindly downstream. Every invalid transform is logged (not silently dropped). `EgoMotionUnreliableError` is raised only if the longest contiguous unreliable span exceeds `max_unreliable_span_sec` — a single bad pair doesn't fail the video, consistent with Phase 2/3's "log per-instance, raise only past an aggregate threshold" pattern. Output is index-aligned 1:1 with every video frame (frame 0 is an identity placeholder — no previous frame to compare against — rather than a length-T-1 array), so Phase 5 can zip it against MediaPipe/CoTracker output without off-by-one bookkeeping.

**Caching:** `run_ego_motion_on_video_cached()`, keyed on `(video_id, hash(ego_motion sub-config + mediapipe sub-config + pinned model sha256 + project.seed))` — includes MediaPipe (drives the exclusion mask) and the seed (changes RANSAC's actual output) in the cache scope.

**Config:** new `ego_motion:` section — `max_features/quality_level/min_distance` (goodFeaturesToTrack), `roi_exclusion_dilate_px` (20), `ransac_reproj_threshold`/`min_inlier_ratio` (3.0/0.5, matching the Phase 0.5 skeleton's example), `max_rotation_deg`/`min_scale`/`max_scale` (validity bounds), `max_unreliable_span_sec` (2.0). No separate seed field — reuses `project.seed` per CLAUDE.md's "RNG/RANSAC seed" phrasing (they're treated as one concept, not duplicated config surface). All schema-validated, including a cross-field check that `min_scale <= max_scale`.

## Phase 5 — Ego-Motion Corrected CoTracker Trajectories (done)

**`src/hybrid/corrected_trajectory.py`:** removes the estimated camera motion (Phase 4) from the raw CoTracker point trajectories (Phase 3). Each frame's ego-motion transform maps "frame t-1 background coordinates" to "frame t coordinates"; composing these frame-by-frame gives a cumulative transform `C_t` from frame 0's reference frame to frame t's. Every tracked point is corrected by applying `C_t^-1` — re-expressing its frame-t observation in frame 0's fixed coordinate system, so a point that's truly stationary in the real world reads as constant regardless of camera motion, and CPR motion (which the camera doesn't explain) survives as the residual. Implemented with **complex-number arithmetic** (`z = x+iy`, transform `z' = a*z+b`, `a = scale*e^(i*rotation)`) rather than repeated 2x3 matrix products — composition (`a2*a1, a2*b1+b2`) and inversion (`(z'-b)/a`) are then plain scalar complex ops, which stayed numerically clean chained across 500+ frames in testing (verified: cumulative scale on the sanity-check video landed at 1.05x, not runaway). No caching wrapper — this is a cheap pure-numpy transform of two already-cached upstream results, not an expensive branch.

**Correctness proof (not just plausibility):** the core test independently simulates a real-world-stationary point pushed forward through a sequence of random per-frame camera transforms (written directly in the test, not by calling the module's own composition code — a true external check, not tautological), feeds those "observed" positions in as CoTracker's raw trajectory, and asserts the corrected output is constant to `1e-6` — i.e., a point the camera moved is recovered as not having moved at all, which is exactly what this phase is for.

**Tests (`tests/test_corrected_trajectory.py`, 7 tests):** identity composition, cumulative-transform composition matches independent manual computation, the stationary-point recovery proof above, a no-op check when ego-motion is all-identity (corrected == raw exactly), a frame-index-mismatch alignment error, and diagnostic passthrough (visibility, raw motion, ego-motion confidence). All fast/pure — no model or video I/O needed (consumes already-tested Phase 3/4 outputs directly). Full suite: **110/113 tests passing** (113 total incl. 3 slow, run separately in earlier phases), ruff clean.

**Real-data sanity check** (`video3_development.mp4`, chained through cached Phase 2->3->4 output): raw `tracker_motion_y` range **501px**, corrected range **153px** — a substantial reduction. Investigated rather than accepted at face value: final cumulative scale **1.05x**, cumulative rotation **7.3°**, cumulative translation **~217px** over the video's 17s/509 frames — all within sane bounds (no numerical blow-up; the `>3x or <1/3x` drift-warning added in this module didn't fire). Correlation between raw and corrected signal: **0.939** — high enough to indicate the periodic (CPR) structure survives; what's being removed looks like a slowly-varying drift/trend component (physically plausible: genuine cumulative head sway over 17s of physical exertion during compressions), not the oscillatory signal itself. This reduction is *not* proof the correction improves final CPM accuracy — that's an empirical question Phase 14's ablation (comparing CoTracker-alone vs. CoTracker+affine-compensation) is specifically designed to answer, not something to claim here.

**Decisions:** (1) Complex-number similarity-transform representation over repeated matrix multiplication — more compact composition/inversion code, same math. (2) No cache for this phase — recomputing a cheap array transform from two cached results isn't worth cache-management overhead. (3) Flagged (didn't investigate further) a known limitation of the per-frame-pair, no-global-consistency ego-motion design (Phase 4): cumulative drift has no loop closure or bundle adjustment, so absolute correction quality could degrade on much longer videos than this dataset's (~17-30s) clips — not an issue here, worth remembering if this pipeline is ever pointed at longer footage.

## Phase 6 — Farneback Optical Flow (done)

**Refactor before new code:** promoted two ego-motion helpers to `mediapipe_roi.py` as public functions — `roi_exclusion_mask()` and `build_roi_lookup()` (per-frame ROI, forward-filled across MediaPipe detection gaps) — since Phase 6 needs the exact same ROI-masking/lookup logic Phase 4 already built and tested. `ego_motion.py`'s private names now alias the public versions (same signatures, its own tests untouched, verified passing before writing Phase 6 code).

**`src/hybrid/optical_flow.py`:** dense Farneback flow (`cv2.calcOpticalFlowFarneback`) between consecutive frames, split into a foreground reading (within the current CPR ROI) and a background reading (outside it) — never a single whole-frame mean, per spec. `flow_motion_y(t)` = foreground - background (the residual, CPR-only signal), needing no cumulative composition since flow is already a frame-to-frame differential, unlike Phase 5's absolute point positions. `OpticalFlowUnstableError` raised (logged always, raised only past `max_unstable_span_sec`) using the same `longest_bad_run` pattern as Phases 2-4.

**Real correctness bug found and fixed during the sanity check, not just a tuning tweak:** the first implementation used a **plain median** of Y-flow within the ROI for the foreground reading. On real footage this stayed pinned within +/-0.04px across all 509 frames of `video3_development.mp4` — while CoTracker's *already-validated* tracks showed real ~8px mean / 29px max frame-to-frame motion over those same frames. Investigated rather than shipped: printed the raw per-pixel flow distribution inside the ROI at a specific frame pair — min/max were -5/+31px (real motion clearly present) but the 25th/75th percentiles were 0.00/0.42px. **Root cause:** the Phase 2 ROI is deliberately generous (hand + wrist + forearm + margin, built for good CoTracker seeding), so most of its pixels are static skin/background at any instant; only whatever part of the hand is actually mid-stroke carries the compression signal, and a plain median is dominated by the static majority. Tried the tight MediaPipe hand bbox instead of the padded ROI — same problem, still median~0. Fix: `foreground_flow_y` is now the median Y-flow of only the **top `(100 - motion_percentile)`% most-moving pixels by magnitude** within the ROI (new `motion_percentile` config field, default 75 = top quartile). Verified against 20 consecutive real frames before adopting: the fixed statistic traced a clean half-cycle (-8 -> 0 -> +8 -> 0 -> -8px) matching a plausible compression period, while the plain median stayed flat at every one of those 20 frames.

**Config:** new `optical_flow:` section — Farneback params (`pyr_scale/levels/winsize/iterations/poly_n/poly_sigma`, matching the Phase 0.5 skeleton's example), `motion_percentile` (75.0, the fix above), `max_flow_magnitude` (50.0, instability sanity bound), `max_unstable_span_sec` (2.0). Schema-validated (`pyr_scale` in (0,1), `motion_percentile` in [0,100), counts >=1).

**Tests (`tests/test_optical_flow.py`, 10 tests):** identity-frame, config-hash sensitivity, real-`cv2`-on-arrays foreground/background separation with known pixel shifts (large frame/ROI relative to Farneback's smoothing window, to avoid boundary-blend contamination — an early version of this test failed for exactly that reason and was fixed by enlarging the scenario, not by changing the implementation), a **regression test locking in the motion-percentile fix**: ~30% of a synthetic ROI genuinely shifted, ~70% static, asserting the filtered median recovers the true minority signal (a plain median would read ~0 here, matching the real-data failure mode) — this test itself needed two iterations to get the moving-region proportions realistic (a first attempt at a 2%-moving/98%-static edge case was too extreme relative to what real footage actually showed and didn't reliably pass; adjusted to the ~30% proportion the real-data investigation demonstrated). Plus an instability-threshold test (using a real small recoverable shift with a very low threshold, since pure-noise-texture large synthetic shifts are adversarial for Farneback and don't reliably reproduce a genuinely large measured magnitude) and 2 caching-wrapper tests. Full suite: **120/123 tests passing** (3 slow deselected), ruff clean.

**Real-data sanity check** (`video3_development.mp4`, same video as Phases 2-5): **509/509 frames valid**, no unstable spans. After the fix: `foreground_flow_y` range **[-11.82, 9.64]px** (std 4.06 — real variation, not flat), `flow_motion_y` (residual) range **17.22px**. Runtime ~1042s cold (slower than earlier phases' per-frame classical-CV cost; not investigated further since correctness was the priority here — worth profiling in Phase 15 if optical flow becomes the pipeline's bottleneck), cache hit confirmed working (same mechanism as other cached branches).

**Decisions:** (1) `motion_percentile`-filtered median over plain median or mean — directly targets "the moving subset of a mostly-static generous ROI," which is exactly the failure mode found. (2) Applied the percentile filter only to the *foreground* reading, not background — background flow (camera-wide motion) already showed sensible non-degenerate variation with a plain median (consistent with Phase 4's ego-motion RANSAC achieving 0.97 inlier ratio on the same background: it's spatially uniform, unlike the foreground). (3) This finding is a reminder to keep validating every phase against real footage rather than trusting synthetic tests alone — the synthetic tests for `_compute_frame_flow` passed even before the fix (they used uniform-motion patches, which don't exercise the majority-static-minority-moving failure mode); only the real-data run caught it.

## Phase 7 — Motion Waveform Generation (done)

**`src/hybrid/motion_wave.py`:** fuses the two CPR motion signals built so far — `corrected_tracker_motion_y(t)` (Phase 5) and `flow_motion_y(t)` (Phase 6) — into one `motion_wave(t)`. Never a raw average (spec explicitly rules this out; the two signals live on very different scales — tracker: pixel-position deltas over hundreds of px, flow: single-digit per-frame displacement). Each signal is first **robustly standardized**: median-centered, MAD-scaled (`_robust_standardize`, consistency constant 1.4826 so the scale is comparable to a std-dev for an approximately-normal signal) — robust to occasional outlier frames the way a mean/std z-score wouldn't be, and one of the spec's explicitly suggested methods. A degenerate (constant or all-NaN) signal normalizes to all-zero/all-NaN rather than dividing by zero.

**Confidence weighting:** `tracker_weight(t) = mean_point_visibility(t) * ego_motion_confidence(t)` — needs *both* good CoTracker visibility (Phase 3) *and* a reliable ego-motion correction (Phase 4, passed through by Phase 5) to trust the corrected trajectory at that frame; a RANSAC failure that degrades the correction should reduce trust in the corrected signal even if CoTracker itself was tracking fine, so both factors multiply rather than either alone gating the weight. `flow_weight(t)` is 1.0 when that frame's optical flow was valid (Phase 6), else 0.0 — deliberately binary, not a smoothed function of flow magnitude, since large flow magnitude is the *desired* CPR signal, not something to penalize; only the explicit instability flag should zero it out. `motion_wave(t)` is the weight-normalized combination of the two standardized signals, with NaN only where *both* weights are ~0 (both branches untrustworthy simultaneously) — everywhere else, NaN-valued signal contributions are neutralized to zero before weighting rather than propagating (`NaN * 0` is `NaN` in IEEE754, would have silently poisoned otherwise-good frames). Raw signals, normalized signals, per-frame weights, and the fused wave are all kept on `MotionWaveResult` for later debugging, per spec. `WaveformAlignmentError` if the tracker and flow results don't cover the same frames. No caching wrapper — cheap pure-numpy fusion of two already-cached results, same reasoning as Phase 5.

**Tests (`tests/test_motion_wave.py`, 10 tests):** `_robust_standardize` correctness against hand-computed median/MAD, degenerate-constant-array handling (all-zero, not NaN/inf, no numpy warnings — an early version triggered "All-NaN slice" `RuntimeWarning`s on an all-NaN input; fixed by special-casing that before calling `nanmedian`, verified clean by re-running with warnings promoted to errors), NaN passthrough. Fusion tests: frame-mismatch error, full-weight case equals the plain average of the two normalized signals, tracker-only (flow always invalid) and flow-only (tracker always invisible) isolation cases collapse exactly to the trusted signal, both-zero-weight frames produce NaN, ego-motion confidence correctly scales tracker weight, raw-signal passthrough. Full suite: **130/133 tests passing** (3 slow deselected), ruff clean.

**Real-data sanity check** (full chain: Phase 2->3->4->5->6->7 on `video3_development.mp4`): 509/509 frames, no NaNs in the final `motion_wave`. `tracker_weight` mean 0.967 (min 0.551, tracking the ego-motion confidence dip already seen in Phase 4/5); `flow_weight` constant 1.0 (Phase 6 found zero unstable frames on this video). Both normalized signals land in comparable ranges (~[-2, +2]) as designed. **Correlation between the two normalized signals is only 0.106** — investigated, not just noted: this has a natural explanation rather than indicating a bug. The tracker signal is position-like (median Y of tracked points) while the flow signal is velocity-like (frame-to-frame displacement); for an oscillatory signal, a quantity and its derivative are intrinsically out of phase (a sine and its cosine derivative correlate near zero despite sharing the same frequency), so low linear correlation between a position-type and a velocity-type reading of the *same* periodic motion is expected, not evidence the two branches disagree about the underlying compression rate. Whether averaging two out-of-phase signals in the time domain (rather than, say, phase-aligning them first) helps or hurts final CPM accuracy is exactly what Phase 14's ablation ("F — Tracker + flow fused motion") is designed to test empirically — not something to resolve by inventing new logic beyond this phase's spec.

**Decisions:** (1) MAD-based robust standardization over z-score, per spec's explicit suggestion and to avoid outlier frames skewing the scale. (2) Binary flow weight (valid/invalid) rather than a magnitude-graded one — large flow magnitude is signal, not noise, for this application. (3) Multiplicative (not additive/max) combination of visibility and ego-motion confidence for tracker weight — both must hold for the corrected signal to be trusted. (4) No config section for this phase — the fusion behavior is fully determined by upstream per-branch confidence signals already exposed via config in Phases 2-6; nothing here is an independent CPR-domain tunable in the way Butterworth cutoff or peak prominence will be.

## Phase 8 — Butterworth Filtering (done)

**Dependencies:** installed `scipy` (1.15.3) and `PyWavelets` (1.8.0) — the latter isn't needed until Phase 9's CWT estimator, installed alongside scipy now since both were missing and this is a natural point to add them together.

**VFR handling (the core design problem for this phase):** `motion_wave(t)` (Phase 7) is irregularly sampled — Phase 1 confirmed real inter-frame intervals vary (0.033-0.042s on real footage) — but a Butterworth filter's frequency response is only mathematically defined for a uniformly-sampled signal. `src/hybrid/filters.py` resamples onto a uniform grid via linear interpolation (`_resample_to_uniform_grid`) at a **nominal sample rate derived from the median inter-frame interval** (`_nominal_sample_rate` — median, not mean, so an occasional dropped/duplicated frame doesn't skew the estimate) purely for this filtering step. This doesn't violate CLAUDE.md's "preserve real timestamps, don't assume 1/FPS" rule — the original per-frame timestamps aren't touched or reinterpreted anywhere else in the pipeline; this module returns its own `uniform_timestamps_sec` as a distinct, clearly-separate artifact, only for the operation that mathematically requires it.

**`src/hybrid/filters.py`:** `apply_butterworth_filter()` resamples, designs a Butterworth band-pass (`scipy.signal.butter`, order from config), validates `0 < low < high < Nyquist` against the video's *actual* nominal rate (schema-level validation in Phase 0.5's `FilteringConfig` only enforces `low < high`, since Nyquist depends on the per-video sample rate, unknowable at config-load time — this runtime check is what actually enforces the "stay within Nyquist" requirement), and applies it with **zero-phase `scipy.signal.filtfilt`** (no time lag — appropriate since the whole video is available offline, unlike a causal streaming filter). Raises `FilteringError` (new exception) on an invalid band, an all-NaN or near-empty signal, or a resampled signal too short for `filtfilt`'s default padding requirement (`> 3*max(len(a),len(b))`) — caught and surfaced explicitly rather than letting scipy raise an opaque internal error.

**Config (`filtering:`):** `butterworth_low_hz`/`butterworth_high_hz` default **1.0/3.0 Hz (60/180 CPM)** — the exact values from the Phase 0.5 skeleton's own example. Deliberately **wider** than this dev set's observed GT range (69.23-105.88 CPM, see Phase 0's table): a physiologically-motivated clinical band, not fitted tightly to the 6 dev videos, since a band tuned to their exact range would risk not generalizing to the held-out test set (never touched, per CLAUDE.md rule 2) if it happens to have compressions outside that narrow window. `butterworth_order` defaults to 4. Schema-validated: both frequencies > 0, `low < high` (cross-field `model_validator`), order >= 1.

**Tests (`tests/test_filters.py`, 13 tests):** nominal-sample-rate correctness on uniform timestamps and robustness to VFR-like jitter (recovers the true 30Hz rate within 5% under +/-2ms random jitter), resampling recovers a known linear signal exactly, NaN-skipping and all-NaN-raises behavior, Nyquist/ordering validation errors. The two most important: **in-band-preserved / out-of-band-attenuated** — a synthetic composite signal (1.5Hz in-band sine + a much-larger 0.05Hz drift + 10Hz noise, both well outside the [1,3]Hz band) filters down to something whose amplitude and shape (>0.9 correlation) match the pure in-band component alone, ignoring `filtfilt`'s edge-transient region; and **zero-phase verification** — a pure 1.5Hz sine's filtered peak lands within 10% of one cycle of the true unfiltered peak's expected location, ruling out the time-lag a causal filter would introduce. Full suite: **143/146 tests passing** (3 slow deselected), ruff clean.

**Real-data sanity check** (full chain, Phase 2->8, `video3_development.mp4`): resampled to a clean uniform 30.000Hz, 509 frames; filtered signal std dropped from 0.63 to 0.43 (drift/noise attenuated, as designed). As an informal eyeball check *only* (not one of Phase 9's real estimators, and GT was never fed into anything upstream — this is a post-prediction comparison, exactly what CLAUDE.md permits) — a simple rising-zero-crossing count on the filtered signal gives **104.8 CPM**, against this video's **GT of 105.88 CPM**: within ~1%. Strong end-to-end evidence the Phase 2-8 chain is producing a physically meaningful periodic signal before Phase 9's real estimators are built.

**Decisions:** (1) Median-interval resampling for the uniform grid, not the video's reported average FPS metadata — computed directly from the actual per-frame timestamps already flowing through the pipeline, staying consistent with Phase 1's "use real PTS, not assumed FPS" principle even at the point where uniform sampling becomes unavoidable. (2) Filter band kept at the spec skeleton's literal suggested values rather than narrowed to the dev set's observed range — an explicit generalization safeguard, not an oversight. (3) No caching wrapper — cheap scipy operations on a short array, same reasoning as Phases 5 and 7.

## Phase 9 — Four Classical Rate Estimators (done)

**Dependencies:** installed `scipy` and `PyWavelets` in Phase 8 already cover this phase's needs (`pywt.cwt` for CWT, `scipy.signal.find_peaks` for peak detection).

**`src/hybrid/estimators.py`:** four independent estimators, each taking the Phase 8 filtered/uniform-rate signal and reporting its own CPM + confidence, per spec. None hard-codes or nudges toward the known 30-compression count (CLAUDE.md rules 11/13) — each just reports whatever periodicity it finds in its own configured search band (`estimators:` config section, separate from `filtering:`'s Butterworth band so each technique is independently tunable in Phase 15).

- **CWT** (`estimate_cwt`): dominant-power scale within `cwt_freq_range_hz`; confidence = that scale's power share of total in-band power. **Found and fixed a real resolution problem before trusting this on real video**, exactly per spec's testing requirement: a plain linear integer scale grid (`1, 2, 3, ...80`) gives very coarse, nonlinear frequency resolution in the CPR band (`freq(scale) ~ 1/scale`) — the synthetic 100-CPM test signal recovered as 97.5 CPM, outside the ±2 CPM tolerance. Fixed by targeting a linearly-spaced frequency grid directly (`_scales_for_target_frequencies`, inverting `pywt.scale2frequency`) instead of a naive scale sequence — recovers 99.89 CPM on the same synthetic signal. Also added an explicit Nyquist check (`high_hz >= sample_rate/2` raises `EstimatorError`) since the new frequency-targeting design made the old "no scale in band" fallback check unreachable (removed as genuinely dead code rather than left in).
- **Autocorrelation** (`estimate_autocorrelation`): dominant lag within `autocorr_lag_range_sec` (0.3-1.0s, matching the Phase 0.5 skeleton's example, inverse of the 1-3Hz band); confidence = normalized autocorrelation value at that lag.
- **FFT** (`estimate_fft`): Hanning-windowed (reduces spectral leakage) dominant bin within `fft_freq_range_hz`; confidence = squashed spectral SNR (`snr/(snr+1)`, mapping unbounded SNR into [0,1)).
- **Peak detection** (`estimate_peaks`): `scipy.signal.find_peaks` with configurable `peak_min_distance_sec`/`peak_prominence`; CPM from the **median** inter-peak interval (robust to one bad interval); confidence = `1 - coefficient_of_variation` of intervals (clipped to [0,1]). Reports whatever peak count it finds — no assumption of a fixed compression count, per spec.

**Config (`estimators:`):** matches the Phase 0.5 skeleton's example values almost exactly — `cwt_freq_range_hz`/`fft_freq_range_hz` (1.0-3.0 Hz), `autocorr_lag_range_sec` (0.3-1.0s), `peak_min_distance_sec` (0.35), `peak_prominence` (0.3) — plus `cwt_wavelet` ("morl") and `cwt_num_scales` (80) needed for the CWT implementation. Schema-validated (ranges positive and ordered, `cwt_num_scales >= 2`).

**Tests (`tests/test_estimators.py`, 17 tests) — the spec's explicit mandatory testing gate:** every estimator gets a synthetic 100-CPM (1.6667Hz) sine, a noisy version, and a version with 2 dropped cycles, asserting recovered CPM within tolerance (±2 CPM clean, ±5 CPM degraded) before any estimator is trusted on real video — exactly the pattern spec's Phase 9 section mandates. Kept the flat `tests/` layout (not `tests/unit/`) for consistency with every prior phase's tests, rather than fragmenting the directory for one file; spec explicitly allows adjusting its suggested structure. Also: Nyquist-violation error tests for CWT/FFT, degenerate-signal (all-zero) error tests for autocorrelation/peaks, and an orchestration test (`run_estimators_on_video`) exercising all four together. Two of my own test premises were initially wrong, not the implementation — a "band unreachable" FFT test used a band that was still technically below Nyquist (fixed to a genuinely-above-Nyquist band), and the CWT resolution bug above. Full suite: **160/163 tests passing** (3 slow deselected), ruff clean.

**Real-data sanity check** (Phase 2->9 full chain, two dev videos): `video3_development.mp4` (GT 105.88 CPM) — **Autocorrelation and Peaks landed exactly on GT (0.00 error)**; FFT -3.33, CWT -0.69. `video1_development.mp4` (GT 90.00 CPM) — all four estimators overshoot by +3.16 to +5.47 CPM, consistently in the same direction (worth watching in Phase 13's full evaluation, not concerning at this stage — still in a physically sensible ballpark). Observed and worth flagging for Phase 11/12: **CWT's confidence is consistently much lower (~0.056) than the other three estimators (0.73-0.98) despite comparable or better accuracy** — a side effect of Morlet wavelets' inherently broader spectral peaks spreading energy across more adjacent scales than FFT's discrete bins, making "dominant scale's share of total in-band power" structurally smaller. Not fixed now (the formula is well-defined and consistently applied, and confidence *cross-estimator calibration* is explicitly Phase 11's job, not Phase 9's) — noted here so Phase 11 doesn't have to rediscover it. Also observed: `video1_development.mp4`'s ego-motion (Phase 4) logged 17 unreliable-transform warnings across its ~600 frames (vs. 0 for `video3`) — real per-video variation in background-tracking difficulty; none individually exceeded `max_unreliable_span_sec`, so no error was raised, exactly as designed.

This was validated for real, not just reasoned about: loading the actual downloaded checkpoint produced exactly 226 weights against exactly 226 mapping entries, zero shape-mismatch errors.

**Isolated environment (`.venv-tf`, ADR 0003):** TensorFlow 2.21.0 + opencv-python-headless + scipy, kept separate from the main venv per the Phase 0.5 default (unlike CoTracker's torch, which turned out fine to merge into the main venv in Phase 3 -- TF was never checked for that and the checkpoint/dependency footprint alone justifies isolation here). `src/hybrid/repnet_branch.py` (main venv) invokes `run_repnet.py` via `subprocess.run` with a timeout, parses a JSON result file, and wraps it in a typed `RepNetResult`. `Makefile` gained an `install-repnet` target documenting the setup, plus fixed `install` to use the CPU-only torch index (matching what CI already did since Phase 3 -- the Makefile itself had never been updated for that, a small latent inconsistency fixed incidentally while touching the file).

**Checkpoint (`hybrid/models.py`):** three files (`checkpoint`, `ckpt-70.index`, `ckpt-70.data-00000-of-00001`, ~295MB total) from `storage.googleapis.com/semantic_repetitions/repnet_ckpt/`, each pinned by URL + sha256 via the same `PinnedModel`/`ensure_model()` pattern Phase 2 established for MediaPipe -- `ensure_repnet_checkpoint()` downloads/verifies all three into `models/repnet_ckpt/` (gitignored) and returns that directory. Pretrained only, never fine-tuned (CLAUDE.md rule 4).

**Not a pipeline failure when RepNet finds nothing:** per CLAUDE.md rule 11 and the Phase 12 fusion design, "RepNet found no periodicity it trusts" is a valid low-confidence *result* (`cpm: null, confidence: 0.0`, with a `reason` string), not something to crash on -- `RepNetUnavailableError` is reserved for actual infrastructure failures (missing venv/checkpoint, subprocess crash or timeout, unreadable output). `run_repnet.py`'s `main()` never nudges its output toward any known count; it reports exactly what the model predicted.

**Config (`repnet:`):** `threshold`/`within_period_threshold` (0.2/0.5, the notebook's own defaults), `strides` ((1,2,3,4)), `batch_size` (4 -- reduced from the notebook's GPU-tuned 20 for this CPU-only machine), `constant_speed`/`median_filter`/`fully_periodic` (False/True/False), `subprocess_timeout_sec` (1800). Schema-validated.

**Caching:** RepNet is explicitly "the most expensive branch" per spec -- always cached via the same `CacheManager` pattern as every other branch, keyed on `(video_id, hash(repnet sub-config))`.

**Tests (`tests/test_repnet_branch.py`, 9 tests):** all fast/offline -- monkeypatch `subprocess.run` and the checkpoint/venv existence checks, so none of them actually invoke TensorFlow. Cover: platform-specific interpreter path resolution, missing-venv detection, successful-result parsing, the "no periodicity found" (`cpm: None`) path, subprocess-failure and timeout both raising `RepNetUnavailableError`, and cache hit/config-change behavior. The vendored `src/repnet_env/` code is intentionally *not* unit-tested with the main suite (it needs the isolated TF venv, and its correctness was instead verified directly against the real checkpoint below) -- `ruff` still lints it since it lives under `src/`. Full suite: **169/172 fast tests passing** (3 slow deselected), ruff clean.

**Real-data verification (both the vendored model directly, and the full main-venv subprocess bridge):** loading `ResnetPeriodEstimator` + applying the checkpoint mapping against the real downloaded checkpoint: **226/226 weights matched, zero shape errors**. Running `run_repnet.py` directly on `video3_development.mp4`: succeeded, `cpm=92.66`, `confidence=0.66`, `chosen_stride=2`, ~2-3 min runtime. Running the *same* video through `hybrid.repnet_branch.run_repnet_on_video_cached` (main venv -> subprocess -> isolated venv -> back): **identical result** (92.657 CPM), confirming the bridge doesn't lose precision or introduce discrepancies; 29.9s cold (checkpoint already on disk from the direct test, so this measures model-load + inference only, not download), **0.015s cached**.

RepNet's 92.66 CPM vs. this video's GT of 105.88 CPM (~13 CPM / 12.5% error) is noticeably less accurate than Phase 9's classical estimators, which landed within 0-3.3 CPM on the same video. Not treated as a bug -- RepNet is a general-purpose, class-agnostic repetition counter never trained on CPR-specific or egocentric-smart-glasses footage, applied zero-shot; a moderate confidence (0.66, lower than the classical estimators' 0.73-0.98) is itself a reasonable signal that this branch is less certain here, exactly what Phase 12's confidence-weighted fusion is designed to act on. Whether RepNet's inclusion helps or hurts the final hybrid CPM is an empirical question for Phase 14's ablation ("G -- RepNet alone" vs. "H -- Full hybrid"), not something to prejudge from one video.

**Decisions:** (1) Vendor-from-notebook over reimplementing from the paper -- "prefer official pretrained implementations" (CLAUDE.md rule 15) and reimplementing from scratch would have meant guessing at architecture details the checkpoint's weights are keyed to exactly. (2) Subprocess + isolated venv over attempting to merge TF into the main venv (unlike CoTracker/torch in Phase 3) -- the Phase 0.5 default, and not worth the risk of finding out mid-pipeline that mediapipe's TFLite runtime and full TensorFlow collide. (3) `batch_size=4` default (vs. the notebook's GPU-tuned 20) for this CPU-only machine -- Phase 15 can retune if needed. (4) Variant B (stabilized input) deferred, not attempted -- explicit scope decision, not a gap discovered later.

## Phase 11 — Confidence Calculation (done)

**Scope note:** every branch built in Phases 2-10 already computes and normalizes its own confidence inline where it's derived — Phase 11 doesn't recompute anything; it's a consolidation + validation + documentation pass, per spec's actual ask ("normalize confidence values to a consistent range... document how each confidence score is calculated").

**`src/hybrid/confidence.py`:** `collect_confidences()` gathers all nine branch confidences (MediaPipe detection rate, mean CoTracker visibility, mean ego-motion inlier confidence, optical-flow valid-frame fraction, and the four classical estimators' + RepNet's own confidence) into one `BranchConfidences` dataclass, and validates every value is genuinely within `[0.0, 1.0]` — raising the new `ConfidenceRangeError` if a branch's own normalization ever produces something out of range, catching a bug at the boundary before it can silently skew Phase 12's fusion weights. The module docstring is the consolidated documentation spec asks for, one line per branch, pointing back to the phase/module that actually computes it (the authoritative documentation stays there, not duplicated).

**Design note:** MediaPipe/CoTracker/ego-motion/optical-flow confidences don't feed Phase 12's CPM fusion directly — they already did their weighting work upstream, in Phase 7's `tracker_weight`/`flow_weight`. They're still collected here so the complete per-video confidence picture exists in one place for Phase 16's diagnostics and Phase 13's evaluation tables, rather than scattered across five different result objects a caller would otherwise have to reach into individually.

**Tests (`tests/test_confidence.py`, 4 tests):** happy-path collection against synthetic results for all nine branches (verifying each aggregate — e.g. CoTracker's mean visibility, ego-motion's mean confidence — matches hand-computed expectations), `as_dict()` shape, and two range-validation tests (a value above 1.0, a value below 0.0) confirming `ConfidenceRangeError` fires correctly. Full suite: **173/177 tests passing** (3 slow deselected), ruff clean.

**Real-data check** (full Phase 2->11 chain, `video3_development.mp4`, all values read directly from cache — no recomputation): mediapipe=1.000, cotracker=0.998, ego_motion=0.970, optical_flow=1.000, cwt=0.057, autocorrelation=0.875, fft=0.977, peaks=0.926, repnet=0.662 — every value lands in `[0,1]` as expected, and each matches the individual phase's own real-data numbers exactly (no discrepancy introduced by the collection step). The CWT/RepNet outliers noted in Phases 9-10 are visibly preserved here, exactly the picture Phase 12 needs to weight them down rather than something this phase should paper over.

**Decisions:** (1) A thin collection/validation module, not a recomputation layer — avoids duplicating logic that already lives correctly in each branch. (2) Hard validation (`ConfidenceRangeError`) rather than silently clamping out-of-range values — a branch producing >1.0 or <0.0 confidence is a bug in that branch, not something to paper over here.
